# 面向业务落地的能力演进与探索（2026-11-08）

整理日期：2026 年 11 月 8 日

本文讨论知识服务进入实际业务后的能力演进：持续变化的资料如何生效，业务口径与关系如何支持 Agent 完成任务，多角色如何使用共享知识，以及复杂问题如何取得完整证据。方案基于当前项目的业务模型、来源贡献、图查询、MCP 接口和发布恢复机制，属于后续探索，尚未完成实现或生产验收。

当前能力与边界见[架构设计](架构设计.md)、[实施设计](实施设计.md)和[工程验证与限制](../03-使用与验证/工程验证与限制.md)。已完成的优化与实测结果见[迭代优化设计](迭代优化设计-2026-11-08.md)和[评测说明与结果](../03-使用与验证/评测说明与结果.md)。本文中的业务场景用于设计和验证，不代表已确认的企业需求；公开方案提供可借鉴的机制，其性能和效果不能直接视为本项目收益。

## 1. 选择业务场景与建设顺序

先选一个有明确知识来源、业务负责人和答案依据的场景，建立完整任务样本，再决定能力建设范围。可从已有业务模型延伸两个试点：服务依赖查询侧重关系方向、环境和影响范围；规则或指标辅助查询侧重适用条件、业务口径和版本。首轮只选择其中一个，避免同时扩展多个领域而缺少实际验收。

| 方向 | 实际使用中的问题 | 当前基础 | 建议启动条件 |
| --- | --- | --- | --- |
| 资料更新与时间语义 | 新旧制度如何替换，历史问题适用哪个版本 | 来源贡献、冲突保留、差量维护、准备与发布分离 | 来源开始持续更新时，先做受控替换；历史查询按需求增加 |
| 业务语义与关系 | Agent 是否理解指标口径、依赖方向和适用条件 | 显式业务模型、身份字段、规则、图路径和 MCP | 有业务负责人提供定义、样例和验收依据 |
| 完整证据组织 | 主规则、前提和例外是否同时返回 | 融合召回、重排、来源坐标、详情上下文 | 已发现证据遗漏，且能区分遗漏发生的阶段 |
| 来源权限传播 | 同一实体融合多份资料后，用户可见哪些事实 | 来源贡献与按资料范围取证 | 多角色共享知识且来源权限不同；上线前必须验证 |
| Agent 连续交互 | 消歧后如何继续，部分结果如何处理 | 工具接口、歧义与预算返回 | 接入实际 Agent 任务流程时 |

容量、发布可用性和故障恢复随上述试点一起验证。具体响应时间、更新时限和并发目标由业务确定；现有小样本评测不能作为生产服务承诺。

## 2. 持续更新的知识与时间语义

### 2.1 业务场景与现有边界

制度可能下个月才生效，补充协议可能只修改部分条款，今天录入的记录也可能描述上个月发生的变更。查询“当前适用什么”和“当时为什么这样处理”，需要不同的时间条件。

当前项目维护当前知识，删除与重新导入是两个独立任务。新资料导入失败不会恢复已删除资料，同名文件和上传时间也不建立版本关系。已有贡献撤回和差量重算机制可以作为更新基础，但还不能表达同一来源的连续修订。

### 2.2 探索方案

先设计受控资料替换：由来源系统提供稳定来源标识、修订标识和明确的替换关系；新版本在旧版本仍可查询时完成准备，替换计划同时包含旧贡献撤回、新贡献加入和受影响对象重算。准备失败保留旧版。正式写入开始后发生故障，仍按计划恢复，并保持现有查询门禁；这一阶段不承诺自动回滚或持续可读。

替换还需校验预期旧版本，防止较早提交的修订覆盖已经生效的新修订。同一来源的修订顺序与知识库任务顺序需要一起裁决。部分修订只撤回被替换的声明，不能默认整份补充协议覆盖原合同。两份独立来源相互矛盾时，继续保留冲突和依据，由明确的业务规则或人工确认处理。

在确有历史查询需求后，再增加事实有效期与系统记录时间：业务时间描述事实何时适用，系统时间描述系统何时获知或纠正该事实。查询指定时间时，实体属性、关系、规则和证据都应遵守同一时间条件。日期缺失或含义不清时返回未知，不以导入时间补成业务生效时间。

Graphiti 的实体关系记录包含 `valid_at`、`invalid_at`、`created_at` 和 `expired_at`。Zep 于 2026 年 10 月发布的说明进一步解释了业务时间与系统时间的区别，可借鉴其字段语义和按时间查询思路。[Graphiti 关系模型](https://github.com/getzep/graphiti/blob/main/graphiti_core/edges.py) · [Zep 双时间线设计](https://www.getzep.com/blog/context-graphs-two-timelines-every-fact/)

该参考不直接解决本项目 PostgreSQL、Neo4j 和 Qdrant 的跨存储发布一致性。整库快照、事实有效期和资料修订也是三种不同概念，需要分别定义。

### 2.3 最小验证与代价

构造同一来源的两个修订和一份独立冲突来源，覆盖未来生效、追溯修正、修订乱序、准备失败、发布中断和共享实体贡献保留。检查当前查询与指定日期查询的结果及引用，确认准备失败不撤回旧知识，修复完成后不会混用两个修订。

历史保留会增加存储、索引过滤和迁移成本。业务仅需要当前知识时，先实现受控替换；需要审计或历史追问时，再承担历史查询的复杂度。资料过期、事实被修正和必须彻底删除的资料，应采用不同的保留规则。

## 3. 业务语义与关系支持

### 3.1 业务场景与现有边界

“支付成功率下降了吗”需要明确统计对象、重试处理、时间字段和分母。“支付服务变更影响哪些系统”需要明确服务身份、环境、依赖方向与查询范围。文本相关或实体同名都不足以确定这些条件。

项目已经支持显式模型、实体身份、规则定义、邻居和路径查询，最终回答、问数与业务计算由外部 Agent 执行。后续重点是为一个具体业务建立可验证的定义与关系，并通过现有接口交付给调用方。

### 3.2 探索方案

以指标辅助查询为例，为少量经过业务确认的指标补充定义、统计粒度、适用条件、时间口径、数据字段映射、允许的关联关系、来源与版本。模型抽取可以产生待确认候选，正式采用的计算口径需要业务依据；没有依据时应请求澄清。

检索返回结构化定义和缺失条件，由外部 Agent 或查询执行器完成计算。若“成功率”同时存在订单口径和尝试口径，应先返回选择条件，不能仅凭向量相似度选一个公式。字段或口径变化后，也需要识别哪些规则和已保存查询受到影响。

MetricFlow 通过实体、维度和指标定义组织语义模型，依据实体类型约束关联，防止一对多展开等情况导致错误聚合。可参考其显式语义和关联约束，不必在本项目中复建 SQL 编译与执行能力。[MetricFlow 关联与语义验证](https://docs.getdbt.com/docs/build/join-logic)

若试点选择服务依赖，则沿现有 `query_graph` 验证环境隔离、关系方向和每条边的来源。返回“影响范围”时注明查询深度、截断和知识更新时间。依赖路径可以提供影响线索，但不能仅凭可达关系断言实际故障影响或根因。

### 3.3 最小验证与代价

先由业务负责人确认少量指标或服务依赖样例，覆盖同名异义、缺失条件、错误关联方向、版本变化和范围不完整。分别检查概念定位、条件澄清、关系正确性和引用依据；端到端任务再检查外部 Agent 是否采用了正确口径。

这种能力的主要成本是业务定义维护和来源治理。只有自然语言描述、没有稳定定义和验收依据时，不宜扩大自动规划范围。

## 4. 面向复杂问题的完整证据组织

### 4.1 业务场景与现有边界

规则适用性、合同义务和技术排障往往需要同时读取主体规则、前提、例外和步骤。片段分别相关，并不表示组合后足以回答问题。

现有合同评测中，“终止后授权”存在所需前置条款已经进入候选池、重排后仍遗漏的情况；公开长文也存在跨窗口证据覆盖不足。当前实体详情补段主要改善已命中实体的返回内容，不能统一解决未入库、未召回和选择遗漏三类问题。具体结果见[评测说明与结果](../03-使用与验证/评测说明与结果.md)。

### 4.2 探索方案

先以已知失败样本验证整组证据选择。对问题列出需要核对的主体、条件、例外或依赖项，并把每项关联到候选中的原文依据。关系路径用于发现补充材料，每条边仍需来源支持；图上连通不自动证明结论成立。

按缺口所在阶段采取不同动作：候选已有但未选中时，比较联合选择与当前重排；候选中没有时，限定来源、关系或关键词补检索；原文没有依据时，返回不足。补检索设置总调用数、时间与返回字数上限，预算耗尽后保留缺口说明。

Google 在 2025 年发表的充分上下文研究说明了区分相关内容与足够回答的内容的价值，可参考其证据充分性评估思路。[Google Research：充分上下文](https://research.google/blog/deeper-insights-into-retrieval-augmented-generation-the-role-of-sufficient-context/)

2026 年 8 月的 PAGE-RAG 预印本研究查询局部候选图、来源线索和固定预算下的充分证据选择。可借鉴选择阶段的设计，但截至本文查阅时，其公开仓库只有待开源说明，尚不能据此复现完整实现；本项目应先做小范围独立实验。[PAGE-RAG 论文](https://arxiv.org/abs/2608.29753) · [公开仓库状态](https://github.com/denghk666/PAGE-RAG)

### 4.3 最小验证与代价

第一轮固定候选池、模型和上下文预算，比较当前重排与整组证据选择，测量必要证据覆盖、无依据内容和调用成本。第二轮才允许补检索，另行统计新增召回、调用次数和延迟。两轮都加入无答案、例外条件、冲突来源及独立长文样本，不能只修复已知合同题。

充分性判断本身也可能出错。需要由人工确认的证据集合检查漏判和误判，并重复运行观察波动。收益不能覆盖新增延迟、费用或其他样本退步时，保留现有主链路，或仅在明确的问题类型上启用。

## 5. 多角色使用下的来源权限传播

### 5.1 业务场景与现有边界

同一客户实体可能同时来自公开资料与内部合同。用户可以访问公开资料，却不能访问合同。即使隐藏合同引用，融合后的实体摘要、属性和关系也可能包含合同信息。

项目已有来源贡献与按资料范围组织证据的机制，但领域标签和调用方传入的资料范围不等于授权。生产中的用户身份、可访问来源和权限变化需要由可信授权链路确定。

### 5.2 探索方案

优先定义安全边界。若用户群和知识来源天然分离，可先按知识库隔离。必须共享实体时，再把授权落实到支持该属性或关系的来源贡献，并按可见贡献组织返回结果。可见一条关系不代表可见实体的全部属性。

检索、图路径、详情、原文下载和 MCP 均使用同一授权上下文。未授权原文不能进入重排或回答上下文。尤其要检查融合摘要、向量检索使用的描述、候选数量和缓存，避免隐藏来源通过派生内容泄露。无法证明派生内容仅依赖可见来源时，应重新生成授权范围内的内容或隔离索引。

权限撤回应有明确的生效时限，并使对应缓存与交互续查状态失效。上游权限同步失败时，不能沿用未知授权范围继续放行。由服务端计算过滤条件，不能让调用方任意扩大范围。

Azure AI Search 的公开设计把文档权限作为索引元数据，并在查询时执行授权过滤，可参考其权限传递方式。部分原生集成功能仍为预览状态；它的文档级过滤也不直接解决本项目的多来源实体融合，需要单独设计贡献与派生内容的权限语义。[Azure 文档级访问控制](https://learn.microsoft.com/en-us/azure/search/search-document-level-access-overview)

### 5.3 最小验证与代价

构造两个用户组、公开与受限来源，以及同时受两类来源支持的实体。覆盖直接检索、实体详情、图路径、摘要、缓存命中、原文读取和权限撤回。验收要求是未授权内容不进入返回值和模型上下文，同时可见来源支持的知识仍可使用。

按授权范围重组内容会增加查询成本，预先按角色生成内容则增加存储与失效维护成本。应先根据角色数量、权限变更频率和共享需求选择方案，避免一开始建设通用复杂权限平台。

## 6. Agent 连续交互与结果契约

### 6.1 业务场景与现有边界

用户查询“支付服务的依赖”，系统找到两个同名服务。用户选定一个后，需要继续原查询。检索没有候选、证据不足、查询被截断和维护期间暂不可用，也需要不同的后续动作。

当前接口已返回歧义、范围和预算信息。[检索交互待讨论](../plans/检索交互待讨论.md)记录了两个具体问题：无候选也可能返回 `needs_disambiguation`，选定实体后通常重新调用模型规划。

### 6.2 探索方案

在现有结果契约上明确无候选、待选择、证据不足、部分完成与暂不可用的含义，分别给出缺失条件、候选、已覆盖范围和停止原因。状态是否能自动重试应由原因决定，不能由 Agent 反复尝试直到耗尽预算。

探索保存短期查询状态，绑定已确认的意图、关系方向、范围、业务模型版本和授权上下文。用户补充实体选择后，优先继续已校验步骤。知识、模型或权限变化时重新校验，无法安全复用则明确要求重查。该状态需要期限和服务端校验，不能成为扩大权限的入口。

为完整任务设定共享预算，记录各步骤耗时、模型调用和剩余额度。外部 Agent 负责最终解释或计算，知识服务交付可引用的结果与边界；这样才能判断问题发生在实体定位、图查询、取证还是外部执行阶段。

### 6.3 最小验证与代价

以多轮任务验证同名消歧、用户改选、无候选补充条件、维护后重试、权限撤回和知识更新。比较任务完成率、澄清轮次、重复规划次数、总调用成本与响应分位数。减少一次模型调用只有在查询语义保持正确时才算收益。

短期状态增加过期、并发修改与失效处理的复杂度。确定性步骤可以先复用；缺少可校验的续查条件时，保留明确重查行为。

## 7. 生产运行能力与验收

### 7.1 用业务要求决定发布和扩容设计

当前准备阶段允许旧知识继续查询，正式发布阶段排空在途查询并保持门禁，核验后恢复可见。多 Worker 准备并不等于正式发布可跨机接管，也不代表更新期间持续可读。已有机制和未覆盖范围见[实施设计](实施设计.md)与[工程验证与限制](../03-使用与验证/工程验证与限制.md)。

| 业务要求 | 首先测量或验证 | 达不到要求时的探索 |
| --- | --- | --- |
| 来源变更及时可查 | 从接收变更到发布可见的时间，准备与发布队列积压 | 来源修订检查点、重复与乱序事件处理；按知识库公平调度 |
| 更新时查询可用 | 发布停读时长、在途查询排空时间和超时比例 | 查询绑定已发布代次，新代次核验后切换；确认各存储能保留旧代次后再采用 |
| 多库并发且费用可控 | 单库与多库的 P50/P95、模型并发、令牌量与单位任务成本 | 全局模型限流、按库配额、队列背压和可取消任务 |
| 发布故障可恢复 | 进程退出、写入结果未知、核验失败后的恢复时间和可见状态 | 扩充故障注入；需要跨机接管时设计租约及过期写入者隔离 |

持续可读的代次切换需要图、向量、贡献和详情查询使用一致代次。仅切换向量索引别名不能保证跨存储一致性。旧代次也需等在途查询结束后才能回收，会增加存储和清理成本。业务接受短维护窗口时，先验证现有发布方案。

容量验证使用接近实际的文档规模、更新频率和查询组合，分别测图查询、原文检索与自然语言组合检索。测试记录固定模型、预算、版本、并发和缓存状态，不能把高预算单题成绩换算为默认配置的生产延迟。

### 7.2 形成可复核的业务验收样本

试点样本由业务问题、预期知识或证据、适用时间、用户权限和允许结果组成，覆盖正常查询、歧义、无答案、冲突、旧版本、权限撤回和资料更新。将开发样本与独立验收样本分开，避免围绕已知题反复调参。

分别记录四类结果：

- 知识正确性：实体身份、属性、关系、规则与来源是否一致。
- 证据完整性：必要前提和例外是否覆盖，引用是否支持所交付内容。
- 业务任务结果：外部 Agent 是否采用正确口径、完成澄清并报告范围限制。
- 运行成本：构建与查询耗时、模型调用、费用、更新时效和故障恢复时间。

每次探索都保留基线、成功条件、退步样本和停止条件。参考实现只有在本项目的固定条件对照和独立业务样本上取得可重复收益后，才进入主链路。

## 附录 A：参考文献与后续演进参考点

以下按编号列出论文、实现和官方设计资料。论文注明所引版本，在线文档注明来源及版本边界；“后续参考点”是结合本项目提出的应用思路，尚未验证。正文保留就近链接，本附录通过章节对应关系说明每项资料的用途。

### [1] 时序知识图谱：Zep 研究论文

Rasmussen, P., Paliychuk, P., Beauvais, T., Ryan, J., & Chalef, D. **Zep: A Temporal Knowledge Graph Architecture for Agent Memory**. arXiv:2501.13956v1, 2025-01-20. 预印本。[论文](https://arxiv.org/abs/2501.13956v1)

- **参考内容**：把持续到来的对话与业务数据组织为保留历史关系的时序知识图谱，支持随时间变化的 Agent 上下文。
- **后续参考点（第 2 节）**：在现有来源贡献之上，探索声明的有效期、修正关系和历史检索；为同一事实的不同时间状态保留可追溯依据。先用修订和追溯修正样例验证时间语义，再考虑扩大输入来源。
- **适用边界**：论文主要评估 Agent 记忆任务，不能据此推断本项目合同、业务规则或多存储发布的效果。其历史关系机制也不等于资料原子替换或整库回滚。

### [2] 时间字段与存储表达：Graphiti 实现

Zep / Graphiti contributors. **Graphiti: `graphiti_core/edges.py`**. GitHub 开源实现，所引为 `main` 分支在线文件，未固定提交。[源码](https://github.com/getzep/graphiti/blob/main/graphiti_core/edges.py)

- **参考内容**：`EntityEdge` 中的 `valid_at`、`invalid_at`、`created_at`、`expired_at` 及其存取表达，展示业务有效时间与系统记录时间如何落到关系对象。
- **后续参考点（第 2 节）**：沿关系模型、序列化和查询过滤继续追踪实现，核对未知日期、开放结束时间和失效记录的处理。为本项目定义字段前，先建立“未来生效、补录历史、纠正旧声明”的预期结果表。
- **适用边界**：本次参考定位到关系模型文件，不代表已验证完整时间抽取、冲突裁决和搜索实现。实施时需要固定提交并阅读对应测试，不能只增加四个时间字段就宣称支持历史查询。

### [3] 双时间线的业务解释：Zep 设计说明

Ryan, J., & Kemp, P. **How Zep Context Graphs keep two timelines for every fact**. Zep Blog, 2026-10-29. 官方技术说明。[原文](https://www.getzep.com/blog/context-graphs-two-timelines-every-fact/)

- **参考内容**：区分事实在现实中何时成立，以及系统何时获知或获知其失效；说明为什么最新录入的信息不一定适用于历史问题。
- **后续参考点（第 2、3 节）**：把“当前口径”“当时适用口径”“当时系统已知口径”拆成不同查询需求，构造晚到资料和历史字段映射变化的验收样例。来源修订时间、上传时间和业务生效时间分别定义。
- **适用边界**：这是 Zep 产品的设计解释，不能假定其全部行为与开源 Graphiti 的任一版本一致。自动判定冲突何时生效仍需业务证据，来源时间不能替代事实时间。

### [4] 业务语义与关联约束：MetricFlow 官方文档

dbt Labs. **Joins — MetricFlow**. dbt Developer Hub，动态在线文档；关联行为与所选 dbt/MetricFlow 版本有关。[官方文档](https://docs.getdbt.com/docs/build/join-logic)

- **参考内容**：使用语义模型中的实体定义关联键，根据实体类型限制关联，避免一对多展开或多对多关联造成重复、遗漏；检查关联路径与字段的有效性。
- **后续参考点（第 3 节）**：给指标与规则增加显式粒度、维度、时间口径和允许关联条件；向外部 Agent 交付经过确认的定义与约束。优先验证“口径相同但名称不同”和“名称相同但粒度不同”的任务。
- **适用边界**：借鉴语义建模和关联校验，不默认引入其 SQL 编译器。语义模型中的受控关联也不能直接套用于任意业务关系图；本项目的服务依赖路径仍需独立定义业务含义。

### [5] 证据充分性：Sufficient Context

Joren, H., Zhang, J., Ferng, C.-S., Juan, D.-C., Taly, A., & Rashtchian, C. **Sufficient Context: A New Lens on Retrieval Augmented Generation Systems**. arXiv:2411.06037v3, 2025-04-23；初版发表于 2024-11-09。[论文](https://arxiv.org/abs/2411.06037v3) · [Google Research 官方解读](https://research.google/blog/deeper-insights-into-retrieval-augmented-generation-the-role-of-sufficient-context/)

- **参考内容**：从上下文是否包含足够信息分析 RAG 错误，区分证据不足与模型未正确利用已有证据，并研究证据不足时的选择性回答。
- **后续参考点（第 4、6、7 节）**：为验收题标注必要证据与缺失条件，分别统计取证不足和外部 Agent 使用错误。知识服务返回可核验的不足原因，外部 Agent 决定补问、补检索或停止回答。
- **适用边界**：充分性评估器也会误判，需要人工标注样本校准。不能直接把模型自报“充分”当作事实正确证明；本项目不承担最终回答生成，拒答策略应与外部 Agent 联合验证。

### [6] 固定预算下的整组证据选择：PAGE-RAG

Deng, H., Li, X., Qin, H., & Li, R.-H. **PAGE-RAG: Provenance-Aware Graph Evidence Promotion for Fixed-Budget Multi-hop Retrieval-Augmented Generation**. arXiv:2608.29753v1, 2026-08-30. 预印本。[论文](https://arxiv.org/abs/2608.29753v1) · [作者仓库](https://github.com/denghk666/PAGE-RAG)

- **参考内容**：在已检索候选上建立查询局部图，结合来源与路径线索，在固定最终上下文预算下选择支持材料；候选连通关系只作为待验证的支持假设。
- **后续参考点（第 4 节）**：针对“前置条款已进入候选池但被排除”的失败，固定候选、模型与返回预算，比较当前重排和整组选择。检验主体规则、条件与例外能否共同入选，同时记录无关内容和新增调用成本。
- **适用边界**：选择阶段不能找回候选池中根本没有的证据。查阅时公开仓库仍只有待开源说明，尚无可复现的完整代码；这里只提出实验方向，不据论文指标承诺项目收益。

### [7] 来源授权与查询过滤：Azure AI Search 官方文档

Microsoft. **Document-level access control in Azure AI Search**. Microsoft Learn，动态在线文档；部分原生权限集成标记为预览功能。[官方文档](https://learn.microsoft.com/en-us/azure/search/search-document-level-access-overview)

- **参考内容**：从资料摄取到查询传递文档权限信息，通过安全过滤或身份与权限元数据校验约束可见结果；不同来源与身份体系采用不同接入方式。
- **后续参考点（第 5 节）**：由可信身份确定可见来源，在检索、详情、原文与 MCP 入口使用一致授权；再沿本项目贡献记录检查实体属性、关系、摘要和缓存的派生内容。增加“同一实体具有公开与受限来源”和“权限撤回后续查”的用例。
- **适用边界**：文档级访问控制不直接覆盖多来源融合实体的权限传播。Azure 功能状态与 API 版本需要在实施时复核，本项目也不因采用过滤字段而自动获得同等授权保证。
