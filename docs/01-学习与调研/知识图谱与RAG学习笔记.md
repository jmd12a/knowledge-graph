# 知识图谱与 RAG：概念、工程取舍与项目边界

本文整理知识表示、构建、维护与检索，区分通用概念、曾考虑选项和当前实现。公开资料依据 2026-10-31 调研记录，产品能力以链接文档及部署版本为准。

本项目提供可配置的知识构建、维护和检索服务。图知识库保存当前实体、关系与规则，向量索引辅助寻找对象和原文证据；外部 Agent 负责最终回答、业务计算和问数。完整约定见[架构设计](../02-项目设计/架构设计.md)和[实施设计](../02-项目设计/实施设计.md)，操作与验收分别见[运行指南](../03-使用与验证/运行指南.md)、[评测说明与结果](../03-使用与验证/评测说明与结果.md)。

## 1. 知识表示、存储与 RAG 的分工

### 1.1 几个容易混淆的名称

| 名称 | 主要职责 | 不应混同的概念 |
|---|---|---|
| 知识库 | 组织知识、来源与使用方式的系统或集合 | 不等于某一种数据库 |
| 知识图谱 | 用实体、关系、属性和语义组织知识 | 不等于图数据库软件 |
| 图数据库 | 保存图结构，执行事务、约束与图查询 | 不替应用决定哪些业务事实成立 |
| 向量检索 | 根据语义相似性寻找对象或文本候选 | 相似度不能证明身份相同或关系成立 |
| RAG | 检索外部知识，将证据交给模型生成回答 | 不要求一定使用图 |
| GraphRAG | 使用图帮助检索或组织上下文的一类方法 | Microsoft GraphRAG 是其中一个具体项目 |

知识图谱可独立用于关系分析；GraphRAG 用图组织检索与上下文，不限定数据库。

知识表示、存储更新、检索和回答生成是不同职责，不要求一一对应部署产品。

### 1.2 表、图与向量可以表示同一组知识

贯穿示例：订单服务属于交易域，调用支付服务；支付服务属于支付域。

```text
关系表：services(service_id, name, domain_id)
        dependencies(source_id, target_id, reason)

业务图：订单服务 ──CALLS──→ 支付服务
        订单服务 ──BELONGS_TO──→ 交易域
        支付服务 ──BELONGS_TO──→ 支付域

向量记录：文本 + embedding + 对象 ID / 文档 ID / 原文位置
```

关系表通过关联表和连接表达关系，图数据库把关系作为可直接查询的数据对象，向量记录帮助找到措辞不同但含义相近的描述。三者可以共存。原文保存措辞和上下文，图显式表达已采用的结构，向量负责候选定位。

图节点和边可分别更新。图数据库便于表达路径查询，但性能取决于数据、索引与工作负载，不能断言总比关系数据库快。

## 2. 类型、Schema、本体与实体身份

### 2.1 类型定义不等于实例事实

| 层次 | 示例 | 回答的问题 |
|---|---|---|
| 类型与概念 | 服务、接口、业务域 | 有哪些类别，各自含义是什么？ |
| 实体实例 | 订单服务、支付接口 | 具体有哪些对象？ |
| 关系类型 | `CALLS`、`BELONGS_TO` | 允许怎样的连接，方向表示什么？ |
| 关系实例 | 订单服务调用支付接口 | 哪条关联已经被记录？ |
| 来源证据 | 文档某节、表格某行、原文片段 | 这条知识依据什么？ |

在 Neo4j 属性图中，节点可有多个标签，节点和关系均可携带属性，一条关系有一个关系类型。标签标记类别，不是一张独立的表。若需要查询概念体系，也可以把“服务类型”本身建成节点，用 `INSTANCE_OF`、`SUBCLASS_OF` 表达实例与概念的联系；是否这样建模取决于查询目标。[Neo4j 图模型](https://neo4j.com/docs/getting-started/appendix/graphdb-concepts/)

业务图模型关注如何用图解决业务问题；Schema 描述类型、属性、关系端点及约束；本体进一步说明概念含义、分类和逻辑语义。三者有所重合。GraphRAG 可以采用轻量业务 Schema；只有需要正式语义和推理时，才另行考虑 OWL 等语言及推理器。[W3C OWL Primer](https://www.w3.org/TR/owl2-primer/)

### 2.2 规则的表达、约束和执行要分开

“服务编号唯一”“一个服务必须且只能有一个主归属域”“跨域调用可汇总为域间依赖”分别涉及唯一性、关系数量和规则推导。将这些要求写入提示词、配置或规则节点，只完成了表达；数据库约束、应用校验或推导程序还要实际执行。

Neo4j 的 `MERGE` 按给定模式查找或创建，不会理解别名或自行确认业务身份。唯一性约束可阻止重复身份，但不自动保证身份属性必填，也不能替代任务幂等和关系去重。数据库支持的约束种类还受版本及版本类别影响。[MERGE](https://neo4j.com/docs/cypher-manual/current/clauses/merge/)、[约束说明](https://neo4j.com/docs/cypher-manual/current/schema/constraints/create-constraints/)

### 2.3 身份依据决定知识能否可靠合并

| 情况 | 处理原则 |
|---|---|
| 同一可靠业务编号，名称不同 | 按身份复用对象，保留来源支持的名称或别名 |
| 名称相同，环境或身份范围不同 | 在配置的范围内区分对象 |
| 只有简称或模糊描述 | 查找候选，保留歧义 |
| 多个候选均可能匹配 | 不凭最高相似度直接合并 |
| 来源无法提供完整身份 | 按建模规则保留候选及原因，避免制造确定事实 |

类型配置至少需要含义、边界、属性类型、必填项、身份字段、允许的关系端点和证据要求。只配置“服务”“依赖”两个名称，难以让不同文档得到一致结果。

通用方案可以由模板、样本生成或人工录入模型。本项目采用外部明确提供完整模型的方式：普通导入抽取实例，不自动增加类型；模型修改通过维护任务生效。新增实例是数据变化，改变类型含义、身份规则或关系端点则是模型变化，需要检查已有知识的影响。

## 3. 存储、索引与模型表示

### 3.1 原文、向量和业务图各保留什么

Embedding 将文本转换为数值向量，通常没有将向量精确还原为原文的通用逆运算。因此向量记录必须能回查原文或稳定引用。向量每个维度通常也不对应一个可直接命名的业务字段。

解析、分词、Embedding 与生成解码是不同步骤。查询与文档编码应兼容，不能只按维度判断模型能否混用；内容或配置变化时需检查兼容性并重建索引。

| 可索引的对象 | 编码内容 | 典型用途 |
|---|---|---|
| 图对象 | 名称、别名、类型、描述 | 将口语映射到实体候选 |
| 文档切片 | 原文及标题、章节上下文 | 找证据和未建模内容 |
| 规则或指标定义 | 含义、适用条件、定义说明 | 定位候选后读取完整规则 |
| 领域或社区摘要 | 一组知识的概括 | 总体问题和范围定位，属于可选方案 |

一个对象可以有多种文本表示，但每增加一种索引，也增加更新与失效维护工作。本项目采用图对象索引与文档切片索引两类；未把社区摘要检索作为首版能力。

### 3.2 索引解决访问效率，不能替代业务含义

属性索引用于按编号、日期等值定位或过滤；倒排索引用于查找词项；向量索引用于找近邻；图访问结构用于沿关系寻找邻居和路径。图查询通常先按属性定位起点，再按关系类型、方向与跳数展开。

精确搜索保证给定范围和度量下的真实近邻，近似搜索可能遗漏近邻。HNSW 用多层近邻连接组织向量，IVF 先分组再搜索部分组。HNSW 的内部图表达向量近邻，与业务图的调用、归属语义不同。[pgvector 的精确搜索与近似索引](https://github.com/pgvector/pgvector)

### 3.3 当前项目的存储职责

| 组件 | 当前保存的内容 |
|---|---|
| Neo4j | 当前实体、关系、规则、聚合属性及来源引用 |
| Qdrant 图对象索引 | 图对象的向量与检索 payload |
| Qdrant 文档切片索引 | 切片正文、向量、文档 ID 与原文位置 |
| SQLite | 有效模型配置、资料、任务、来源贡献与未采用候选 |
| 文件系统 | 原始资料、准备检查点和持久化写入计划 |

曾考虑以关系数据库保存实体权威记录、图和向量作为查询视图，也讨论过 PostgreSQL、pgvector 与 Neo4j 的组合。最终采用上表的职责分配；SQLite 不保存另一份当前实体主库或永久切片正文库。

## 4. 从资料到知识：抽取、证据与维护

### 4.1 构建是一条可分别检查的流水线

```text
保存原文并登记任务 → 解析切分 → 按模型抽取或字段映射
                  → 身份对齐 → 类型、端点与证据校验
                  → 保存来源贡献 → 合并知识 → 写图与索引
```

自然语言资料可由 LLM 输出结构化候选，结构化记录可通过字段映射处理，再由程序校验候选并执行固定写入模板，控制身份、范围与重试。

切分控制输入规模并记录证据位置，也可能拆开指代、表格和完整定义。标题、章节路径、必要前文与跨片段身份统一可补充上下文；完整规则缺少必要条件时，应回查相关章节或全文。[Neo4j 图谱构建组件](https://neo4j.com/docs/neo4j-graphrag-python/current/user_guide_kg_builder.html)

### 4.2 抽取候选不等于已采用事实

“订单中心通过 Payment API 完成付款”可以提供实体提及、类型和调用关系候选。写入前仍要确认实体身份、端点类型和原文支持范围。模型给出的置信度可用于排序，不能直接当作已校准的正确概率。

实体介绍与关系证据也要区分：介绍订单服务的文档不一定证明它调用支付服务。关系应能追溯到支持该关系的具体原文，而不只关联一份主题相关文档。

来源贡献需要精确到属性值、描述片段或关系声明。这样才能回答“这个值由谁提供”“删除某份资料后哪些知识受影响”。多份资料支持同一事实时，应保留各自贡献，而不是只在对象上记录一个模糊的文档列表。

### 4.3 删除来源与否定事实不是同一个动作

| 信号 | 应区分的含义 |
|---|---|
| 新资料未提及旧事实 | 可能只是省略，不能自动视为否定 |
| 完整快照明确替代旧版 | 需按来源替换策略撤回旧支持 |
| 新增补充资料或增量事件 | 只处理其中明确表达的变化 |
| 删除一份支持资料 | 撤回该来源贡献，再检查其他支持 |
| 最后一份支持被删除 | 该事实退出当前已证实知识，不等于断言现实中不存在 |
| 来源互相冲突 | 保留可追溯冲突，不能用生成摘要抹平分歧 |

通用知识系统还可能记录业务有效时间、系统获知时间和历史版本。导入时间不能替代事实发生时间，未知的有效时间也不应由程序臆造。本项目首版仅维护当前知识，不提供知识历史查询或历史回滚。

当前资料更新采用“删除成功后重新导入”。同名文件、相似文本或更晚上传时间不触发自动替换。来源删除后重新聚合仍有效的贡献，共享知识只在失去支持时退出；描述与索引也要基于当前来源重建。

### 4.4 一致性需要跨存储的恢复依据

图、向量、元数据和文件不能依靠一个普通数据库事务同时提交。需要明确任务状态、可重放的对象 ID、持久化计划和完成校验，才能在部分写入后恢复。

曾讨论过事务事件表、异步派生刷新、知识发布版本和缓存失效等通用机制。当前采用模块化单体加独立 Worker：同一知识库的维护串行执行，准备阶段允许查询，正式写入阶段通过持久化维护状态与共享/排他文件锁暂停查询。失败恢复复用已保存计划，不重新分配对象身份。

原文先发布再登记资料与任务，避免任务引用尚未保存的文件；上传幂等通过显式键、请求字段和必要的逐块字节比较判断。项目使用随机 UUID，不计算内容摘要、配置指纹或基于哈希的身份。

## 5. 从问题到证据：检索、消歧与覆盖

### 5.1 根据问题选择检索入口

| 问题特征 | 适用入口 |
|---|---|
| 已有对象 ID | 直接读取完整对象或查询图 |
| 名称、业务编号、错误码明确 | 精确或关键词检索 |
| 表述模糊、同义改写 | 向量或混合候选检索 |
| 问邻居、调用链或连接路径 | 确认实体后执行受约束图查询 |
| 需要说明、案例或未建模条款 | 检索原文切片 |
| 问金额、数量、成功率等计算结果 | 找到定义后由外部程序查询和计算 |

例如 `A CALLS B` 表示 A 调用 B。“A 调用谁”沿出边，“谁调用 B”沿入边。反向查询不改变原关系语义；“B 故障影响谁”还需要故障传播、降级和时间条件，不能仅凭调用路径得出最终业务结论。[Cypher 关系方向与路径](https://neo4j.com/docs/cypher-manual/current/patterns/fixed-length-paths/)

图路径直接证明已记录的连接。图中未查到关系，则可能来自资料缺失、抽取遗漏、范围限制或预算截断。只有在明确范围内确认完整性后，才有依据解释为该范围内不存在；其余情况应表达为当前知识未提供证据。

### 5.2 多路候选、重排序与身份确认

多路结果应按稳定 ID 去重。向量、关键词与图检索的原始评分通常不在同一尺度，可以采用经验证的分数校准或排名融合。

重排序对已经召回的较小候选集做更细判断。双编码器分别编码查询和候选，适合大规模检索；交叉编码器联合读取两者，常用于候选重排序。若关键证据没有进入候选集，重排序无法补回遗漏。[Sentence Transformers：Retrieve & Re-Rank](https://www.sbert.net/examples/sentence_transformer/applications/retrieve_rerank/README.html)

多跳结果可以按完整路径及各边证据组织，避免筛选时丢掉中间依据。当前项目用精确匹配和候选检索定位对象；候选不唯一或精确扫描未完成时保留歧义，调用方通过原查询中的提及、字符区间和选定 ID 确认身份。语义相似结果只补候选，不自动证明身份。

### 5.3 Top-K、完整集合与预算不是同一保证

“找几个相关对象”与“列出全部调用者”需要不同的完整性说明。候选检索通常返回 Top-K；图查询的完成性也只针对给定起点、方向、关系类型、范围与跳数成立。

| 预算 | 约束对象 | 需要披露的影响 |
|---|---|---|
| 候选扫描数与结果数 | 名称、全文、向量候选 | 不能把当前看到的唯一候选当作全库唯一 |
| 跳数与候选边数 | 图遍历 | 只能说明预算内探索的范围 |
| 路径条数 | 已发现路径 | 后续路径可能未枚举 |
| 查询超时 | 整次操作及图访问 | 区分失败与已得到的部分结果 |
| 证据条数 | 原文引用 | 可限制证据数量，但不能截短完整规则来伪装完成 |

当前结果通过 `coverage`、告警、歧义和冲突字段说明范围。完整知识对象超过大小预算时返回错误；证据预算不足则说明哪些声明或引用未完整返回。规划失败可降级为显式的部分关键词结果，不能假装已执行原图查询。

自然语言生成查询还涉及执行边界。通用方案可以考虑 Text-to-Cypher，但提示词不能替代程序校验和执行权限。当前使用受约束计划与固定图查询，不开放任意 Cypher 或 SQL。[Neo4j GraphRAG 检索器](https://neo4j.com/docs/neo4j-graphrag-python/current/user_guide_rag.html)

## 6. 业务领域、算法社区与隔离

### 6.1 两种层级按不同依据划分

| 比较项 | 业务领域 | 算法社区 |
|---|---|---|
| 依据 | 职责、流程、术语、业务含义 | 图连接结构和算法参数 |
| 定义方式 | 业务配置，人工或模型辅助归类 | 建图后执行社区发现 |
| 用途 | 组织知识、选择规则、限制处理与检索范围 | 发现主题、聚合摘要、整体检索 |
| 稳定性 | 需要明确且相对稳定的含义 | 可能随数据和参数变化 |

让 LLM 按既定目录分类仍是业务领域分类。一个实体可同时具有业务领域归属和社区成员关系，无需复制实体。当前项目以配置的领域组织和查询范围为主，不包含算法社区建设。

父子领域可以通过成员关系与父子边保存，不要求每层独立数据库。父域可以提供总体视角，但域节点不会自动获得“删除整个子图”“刷新祖先摘要”或“继承权限”的操作语义。维护策略必须由程序落实。

### 6.2 分类、维护范围与权限分别设计

租户解决数据归属与隔离，业务域表达业务职责，知识库或 Workspace 组织资料与配置，权限决定可访问内容，物理数据库提供存储和运维边界。这些范围可以交叉，业务域不自动成为授权边界。

分域要影响实际执行，才有维护意义：导入加载相关定义，对齐限定候选，更新计算受影响对象，查询限制入口、遍历和证据。共享对象按可靠身份关联，跨域调用也需要来源支持；两个域都出现“客户”一词不足以合并对象。

领域感知导入可使用来源提示、章节分类与跨域补充。强制单领域处理可能漏掉事实，共享定义也不代表自动继承父域口径；适用范围应显式说明。

层级深度、摘要层数、算法层数与查询跳数应分开理解，成本还取决于分支与展开边数。层数应依据业务定义和查询需求确定。

## 7. 完整规则、指标口径与问数语义

### 7.1 保存公式不等于定义完整口径

净成交额即使写成“实付金额减成功退款金额”，仍要明确统计粒度、数据来源、关联键、时间归属、过滤状态、去重方式、单位、适用条件和来源。公式相同，时间或粒度不同，结果也可能不同。

例如支付成功率可以按支付单数或尝试次数计算。重试日志一单多行，直接关联后计数可能重复。分母是否包含处理中记录，使用创建时间还是完成时间，分母为零如何处理，都需要业务确认。SQL 可执行并不说明口径正确。

知识抽取规则规定怎样从资料识别知识，业务规则规定对象的行为或计算方法，两类规则要分别管理。语义检索只负责找到候选定义；影响结果的必要条件应完整读取，不能依赖 Top-K 偶然找回。

当前项目保存规则、适用条件和来源供外部系统使用，不执行业务公式、SQL 或最终回答。需要独立检索和完整读取的规则按模型建为实体；属于对象属性或关系条件的规则随对象完整返回。

### 7.2 语义定义是否入图，由查询需求决定

| 需求 | 可以采用的组织方式 |
|---|---|
| 读取一个模型的指标、维度和字段映射 | 模型内配置，通过稳定 ID 引用 |
| 多模型复用同一定义 | 共享配置和依赖 ID |
| 查询字段变化影响哪些指标、报表 | 显式依赖关系，必要时组织为图 |
| 实际金额、数量和统计 | 原业务数据库与受控计算程序 |

配置成员是否入图取决于多级血缘和影响分析需求；业务事实与元数据依赖应有明确语义，避免无目的混合遍历。

文档、数据字典、报表和 SQL 可提供映射候选，业务负责人仍需确认其粒度、公式、时间和关联。已确认问题与正确 SQL 可用于回归，一次临时筛选不能自动推广为默认规则。

Cube、Snowflake Semantic Views 和 dbt/MetricFlow 展示了按语义模型管理指标、维度与关联的做法。配置成员、逻辑依赖节点与 Neo4j 物理节点是不同概念，不能据此断言所有指标都必须或都不应入图。[Cube](https://docs.cube.dev/reference/data-modeling/cube)、[Snowflake Semantic Views](https://docs.snowflake.com/en/user-guide/views-semantic/sql)、[dbt 语义模型](https://docs.getdbt.com/docs/build/semantic-models)、[指标定义](https://docs.getdbt.com/docs/build/metrics-overview)、[已验证查询库](https://docs.snowflake.com/en/user-guide/views-semantic/verified-query-repository)

## 9. 用验证结果判断方案

评估应分别检查抽取、身份、图关系、检索、证据和外部回答。节点和边数量不能证明知识正确，回答流畅也不能证明来源支持。

| 检查点 | 代表问题 |
|---|---|
| 抽取与身份 | 只提到服务是否被误建为调用？别名与同名异物是否正确处理？ |
| 规则完整性 | 定义、条件和引用是否一并保留？是否跨声明拼接了不相容字段？ |
| 图与证据 | 路径的每条边是否有支持？文档片段是否只是主题相关？ |
| 范围与预算 | 所选来源是否引入其他资料的值？部分结果是否被误称为完整？ |
| 删除与恢复 | 撤销部分或全部来源后，共享知识、索引和查询状态是否正确？ |
| 通用性 | 接入第二种业务能否主要替换模型和映射，而复用维护与检索流程？ |

研究图的增益时，应在相同资料、可比模型和预算下，对照向量 RAG、关键词加向量、图查询与证据组织。领域处理可对照统一抽取、单领域和跨域补充，避免将更多模型调用的收益全部归因于图。

本项目已有人工服务目录的机制验证和两份 CUAD 完整短合同的真实调用验证；它们分别提供确定性机制证据和有限的真实文本证据。合同语义与全文召回仍有验收缺口，不能推广为完整公开基准成绩或企业语料质量承诺。具体范围和结果以[评测说明与结果](../03-使用与验证/评测说明与结果.md)为准，模型和候选数据集见[模型服务与数据集调研](../03-使用与验证/模型服务与数据集调研.md)。
