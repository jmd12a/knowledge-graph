# 运行指南

本文说明正式应用的安装、配置、启动、资料维护和任务排错。设计约定见[实施设计](../02-项目设计/实施设计.md)，实际验证范围见[评测说明与结果](评测说明与结果.md)。

## 1. 运行前提

| 组件 | 要求 |
|---|---|
| 操作系统 | Linux 或 WSL Ubuntu；跨进程协调使用 Linux 文件锁 |
| Python | 3.12，依赖范围为 `>=3.12,<3.13` |
| 依赖管理 | 项目独立 `.venv` 和 `requirements.lock` |
| PostgreSQL | 连接可用，应用账号能在目标 schema 创建表和索引 |
| Neo4j | Bolt 连接可用；初始化账号能创建约束和全文索引 |
| Qdrant | REST 连接可用；账号能管理应用集合和点 |
| 模型服务 | 真实 Embedding；文本抽取和自然语言规划另需 LLM |
| 数据目录 | Linux 本地文件系统绝对路径，不使用 `/mnt/` 下的 Windows 挂载目录 |

API 和 Worker 共用数据目录、存储与运行配置。首版每个数据根目录只运行一个 API 和一个 Worker；不使用 Uvicorn 多进程模式，文件锁和原文件目录使用 Linux 本地磁盘。

升级到当前存储结构时，使用空 PostgreSQL 数据库和独立的本地数据目录。需要的资料按新任务重新导入。Neo4j 和 Qdrant 服务可以复用，新知识库按新 ID 建立索引。新机器应先准备可用的数据库服务；`deploy/` 提供应用进程模板，不负责安装数据库。

## 2. 安装独立依赖

以下以 `/srv/knowledge-graph` 为仓库路径。若位于其他 Linux 目录，替换命令路径，并调整 `data_root`、`KG_CONFIG` 及部署模板。

```bash
cd /srv/knowledge-graph
uv venv --python 3.12 .venv
uv pip sync --python .venv/bin/python requirements.lock
uv pip install --python .venv/bin/python --no-deps -e .
```

已有 `.venv` 时跳过创建步骤。不要使用其他工程的虚拟环境或锁文件替代本项目依赖。

## 3. 配置与凭据

首次使用时复制模板，命令不会覆盖已有文件：

```bash
cp --no-clobber configs/app.example.yaml configs/app.local.yaml
cp --no-clobber configs/environment.example .env
chmod 600 .env
export KG_CONFIG=/srv/knowledge-graph/configs/app.local.yaml
```

编辑 `app.local.yaml`，确认存储地址、`data_root`、`llm` 与 `embedding` 的模型端点、名称、维度、距离度量和调用预算。发布示例使用 OpenRouter，设置 `OPENROUTER_API_KEY` 和 `POSTGRES_DSN`；在线规划与后台构建分别配置，Embedding 为3072维。示例检索预算为180秒，代码默认值仍为15秒，可按延迟要求调整。供应商参数与候选资料见[模型服务与数据集调研](模型服务与数据集调研.md)。

密钥只填写到 `.env` 或进程环境变量；使用模板时取消所需变量的注释，配置中以变量名称引用。凭据不写入业务模型、任务参数和版本控制。

配置读取顺序：

1. 保留进程中已有的环境变量。
2. 读取进程环境变量 `KG_ENV_FILE` 指定的凭据文件；未指定时读取当前工作目录的 `.env`。文件值只补充尚未设置的变量，缺少文件时跳过。
3. 读取命令行 `--config` 或 `KG_CONFIG` 指定的 YAML 文件。
4. 用 `KG_*` 环境变量覆盖同名配置项；嵌套对象按 YAML/JSON 解析。

从其他工作目录启动时，显式设置 `KG_ENV_FILE=/实际路径/.env`，并用 `--config` 或 `KG_CONFIG` 指定配置。systemd 也可通过 `EnvironmentFile` 注入变量。`KG_ENV_FILE` 必须在启动前设置，不能由待加载的凭据文件指定自身位置。

可选 `construction_llm` 用于后台抽取、规则组装和摘要，为 `null` 时复用 `llm`。它是完整配置，不是部分覆盖。供应商单次超时与 `retrieval_timeout` 不同，在线请求还受总检索预算限制。`stream: true` 用于接收供应商 SSE 响应；完整帧组装后再校验 JSON，不把中断输出当成成功。`rerank_enabled`、`rerank_candidate_limit` 和 `rerank_timeout` 分别控制候选重排、内部候选上限及重排预算。切片共享的候选阈值由 `chunk_similarity_threshold` 控制，默认 0.97。`chunk_decision_model` 默认使用 OpenRouter Jev，设置为空字符串可关闭语义共享。

检索先融合精确、关键词和向量候选。精确实体命中优先，其他语义查询使用紧凑重排。重排先给各候选保留经过核验的原文，再分配补充片段。重复原文共享引用，章节路径单独提供给模型。模型仅返回候选 ID，缺项由融合顺序补齐。重排超时或返回错误时，结果会附带警告并回退到融合顺序。

`candidate_scan_limit` 限制召回扫描，`rerank_candidate_limit` 限制重排候选，`retrieval_rerank_snippet_chars` 限制每段原文长度，完整请求仍受模型输入预算约束。请求 `limit` 控制各返回分支的 Top K。`coverage` 分别记录融合、实际送模及受预算裁减的候选或补充片段。旧实验配置中的 `retrieval_strategy`、独立通道候选上限和切片到实体扇出设置需从配置文件中删除。

`extraction_scope_policy: structure`（环境变量 `KG_EXTRACTION_SCOPE_POLICY=structure`）启用结构化窗口构建。程序优先使用解析得到的章节和段落边界，并在压平的正文中识别高置信编号标题。首轮抽取按 `extraction_structure_window_chars`（环境变量 `KG_EXTRACTION_STRUCTURE_WINDOW_CHARS`）组窗，默认目标为去重后 10000 个可见原文字符。单个来源块超过目标时，只要完整请求能放入模型硬预算，仍会尽量保持完整。需要时按原切片范围拆分。返回的逐字字段由程序定位，只有检测到候选接到不可见续段时才扩窗补全。默认 `whole` 先尝试全文输入，模型预算不足时按章节和相邻规则单元分批。旧实验配置中的 `chapter` 或 `small_batch` 需改为 `whole` 或 `structure`，并移除 `extraction_small_batch_chunks`。若尚未完成的旧抽取任务保存了已移除的策略，按失败任务重试流程重新准备。已发布的知识可直接使用。可在语言模型配置中设置 `max_context_tokens`，程序在字符上限之外，用请求的 UTF-8 字节数保守估算输入，并为 `max_output_tokens` 预留空间。未配置时使用 `max_input_chars`。

当前真实评测验证了 `json_object` 路径，完整输出 schema 随系统契约发送并由程序校验。原生 `json_schema` 可配置，但其他供应商对条件 schema 的严格方言兼容性尚未实测。

## 4. 初始化与启动

API、Worker 均停止后，执行：

```bash
.venv/bin/kg init-storage --config /srv/knowledge-graph/configs/app.local.yaml
```

初始化检查进程锁，创建 PostgreSQL 表和索引以及 Neo4j 约束和全文索引。请求处理期间不会自动执行迁移。

在两个终端分别运行：

```bash
.venv/bin/kg serve --config /srv/knowledge-graph/configs/app.local.yaml
```

```bash
.venv/bin/kg worker --config /srv/knowledge-graph/configs/app.local.yaml
```

| 入口 | 默认地址 |
|---|---|
| 管理与检索 API | `http://127.0.0.1:8000/api/v1` |
| OpenAPI 页面 / JSON | `/docs` / `/openapi.json` |
| MCP Streamable HTTP | `http://127.0.0.1:8000/mcp` |

```bash
curl http://127.0.0.1:8000/api/v1/health/live
curl http://127.0.0.1:8000/api/v1/health/ready
```

`live` 只检查进程存活；`ready` 检查元数据初始化、图约束与全文索引、向量依赖，不调用模型。Ctrl+C 关闭应用；正式写入中的任务保留维护状态，下次 Worker 按原计划恢复。

`deploy/` 中两个 systemd 文件是可选模板。安装前调整 `User`、`Group`、`WorkingDirectory`、`EnvironmentFile` 和 `ExecStart`，确认服务账号能读取凭据、写入数据目录。应用不自动创建账号或安装系统服务。

### 分布式准备 Worker

在配置文件中启用 `worker_distribution` 后，API 与写入 Worker 使用同一台主机和同一个本地锁目录。准备 Worker 可以部署在其他 Linux 主机，每个实例同时准备一个任务。所有实例连接相同的 PostgreSQL、Redis Stream、MinIO 桶、Neo4j 和 Qdrant，并采用一致的模型、解析和向量设置。每个部署使用独立的任务库、Stream 和私有桶。

准备 Redis 6.2 或更新版本，以及支持条件对象写入的 MinIO。事先创建没有对象版本历史的私有桶。将连接和访问凭据设在 `REDIS_URL`、`MINIO_ACCESS_KEY` 和 `MINIO_SECRET_KEY`，参考配置模板。上线前在实际发行版上验证带 `If-None-Match` 和 `If-Match` 的 PUT，确保关闭标记能拦截迟到写入。 [MinIO S3 兼容性](https://docs.min.io/aistor/developers/s3-api-compatibility/)

初始化使用该配置，然后分别启动以下进程。使用 systemd 时，`deploy/knowledge-graph-distributed-worker@.service` 提供 `@publish` 和 `@prepare` 两个角色入口。`prepare` 可以启动多个，`publish` 和 API 各一个。

```bash
.venv/bin/kg init-storage --config configs/app.local.yaml
.venv/bin/kg serve --config configs/app.local.yaml
.venv/bin/kg worker --config configs/app.local.yaml --role publish
.venv/bin/kg worker --config configs/app.local.yaml --role prepare
```

同一个库的队头准备好后，写入 Worker 才会进入排空、应用与核验。准备失联后由 Redis 移交，同一排队代次用 MinIO 草稿恢复。API 在 PostgreSQL 登记成功后即可响应。写入进程中的投递循环会在 Redis 恢复后补投队头，已登记的正式计划可以在 Redis 暂停期间继续写入。

启用前核对数据库里的原文与计划引用。旧本地引用需要先完成单独迁移，或继续用原配置运行。登记过 MinIO 引用后，常规回退保留 MinIO 可读能力。退役尝试中的空关闭标记会阻止迟到 PUT。只有确认旧进程和在途对象写入都已结束后，才可人工回收这些标记。

任务中断后的恢复动作和查询状态见[实施设计](../02-项目设计/实施设计.md#64-中断与恢复)。

## 5. 业务模型、导入与查询

先校验模型，再创建知识库：

```bash
.venv/bin/kg model validate examples/service-catalog/model.yaml
.venv/bin/kg kb create service-demo examples/service-catalog/model.yaml
```

将返回值代入 `KB_ID`、`JOB_ID`：

```bash
.venv/bin/kg documents upload KB_ID examples/service-catalog/source-a.csv --key import-a
.venv/bin/kg jobs get JOB_ID
.venv/bin/kg jobs issues JOB_ID
.venv/bin/kg describe-model KB_ID
.venv/bin/kg search KB_ID pay-core --no-semantic
```

上传返回202和任务 ID，仅表示已登记。Worker 成功提交后资料成为 active，知识才进入当前查询范围。CSV/JSON 使用显式映射；有多个适用映射时须指定 `--mapping-id`。文本型资料使用真实 LLM 抽取，构建向量索引使用真实 Embedding。

单文件默认限制20 MiB；接收层另给 multipart 封装64 KiB余量，文件自身仍按实际字节检查。相同幂等键按保存的请求字段和原文字节判定：相同请求返回原 ID，不同内容返回冲突。布尔值与数字按类型区分。原请求省略映射时，重放沿用原持久化映射，不被后续模型中的新增映射重新解释。

`search` 返回候选。按返回 ID 使用 `get` 或 `query-graph` 读取完整知识及有方向的图结构；自然语言组合查询使用 `retrieve`。两类文本查询均接受1至4000个 Unicode 字符。调用方应读取 `status`、`coverage`、`conflicts` 和 `unresolved_entities`；语义 Top-K 不代表完整图集合或身份确认。命令参数以各子命令 `--help` 为准。

MCP 提供 `describe_model`、`search_knowledge`、`get_knowledge`、`query_graph`、`retrieve` 五个只读工具。其中 search/query_graph/retrieve 接收 `{kb_id, request: {...}}`，其余参数由工具 schema 定义。资料管理通过 HTTP/CLI 执行。

## 6. 删除、更新与重建

```bash
.venv/bin/kg documents delete KB_ID DOCUMENT_ID --key delete-a
.venv/bin/kg model apply KB_ID examples/service-catalog/model.yaml --key rebuild-model
```

删除撤回该资料的贡献，保留其他来源仍支持的知识。更新采用“等待删除任务成功，再以新幂等键上传”，不按同名文件自动覆盖。

`model apply` 提交 REBUILD；`reindex` 提交 REINDEX。仅改本地 YAML 不会改变在线有效配置。任务排队和准备期间使用旧配置，维护成功后才切换。代码升级也不会自动重新抽取已发布资料，需要时显式提交 REBUILD。

## 7. 任务排错与恢复

先检查任务及候选问题，再决定是否重试：

```bash
.venv/bin/kg jobs get JOB_ID
.venv/bin/kg jobs issues JOB_ID
.venv/bin/kg jobs retry JOB_ID --generation CURRENT_GENERATION
```

将 `CURRENT_GENERATION` 替换为任务详情中的 `retry_generation`。手动重试被接受后代次加一，旧代次再次提交返回 `STALE_RETRY`。

| 状态或错误 | 含义与处理 |
|---|---|
| `PREPARE_FAILED` | 未开始正式知识写入。修复输入或依赖后重试；任务重新排队，按新的有效资料和配置准备 |
| `PREPARATION_SCOPE_UNAVAILABLE` | 旧缓存不能证明当时模型输入范围。保留材料并重新准备；已有正式计划继续按原计划执行 |
| `PREPARED` / `DRAINING` | 已有计划，等待在途读取结束。未开始写入的超时可退回等待，不发布半成品 |
| `APPLYING` / `VERIFYING` / `NEEDS_REPAIR` | 知识查询受门禁阻止，重启或重试沿用原计划、ID 及向量 |
| `CLEANING` / `CLEANUP_FAILED` | 删除已生效，查询可用。原文和检查点清理仍占同库写队头，清理失败可用同一任务重试 |
| `PLAN_INVALID` | 计划缺失、归属或结构不符。核对计划和存储，不手改 READY、不删除恢复目录来跳过检查 |
| `SCAN_BUDGET_EXCEEDED` | 最终索引超过维护扫描预算。提高 `maintenance_scan_limit` 并重启 Worker，按阶段重新准备或继续原计划 |
| `MODEL_QUOTA_EXHAUSTED` | 自动重试停止。保留任务，额度恢复后明确重试 |
| `INVALID_MODEL_RESPONSE` | JSON或结构校验失败；最多一次结构纠正仍不合格时停止，不自动补造字段、引用或完整性声明 |

截断输出、鉴权和额度错误不进入格式纠正。结构通过不能证明语义正确；候选问题与业务复核须分别处理。

任务状态、知识库维护状态和资料 active 是不同概念。健康与任务查询可用，不表示知识查询能绕过门禁。原文下载持读锁直到内容流结束。

成功检查点默认保留24小时。Worker 定期回收过期检查点，并在来源文件排他锁下清理无引用文件；取不到锁就跳过本轮。待修复计划继续保留。
