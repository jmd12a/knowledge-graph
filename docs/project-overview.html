01

一个知识服务，清晰的存储分工

业务模型决定“保存什么、如何认定同一对象”。应用服务负责构建、维护和检索，适配器连接数据库、文件与模型服务。

SYSTEM MAPinterfaces → services → domain / ports

Graph / 知识结构

Neo4j 保存当前实体、关系与可查询属性。业务身份显式配置，避免仅凭名称相似度合并对象。

Vector / 候选定位

Qdrant 分开保存图对象向量、原文切片和共享代表向量，支持关键词与语义召回。相似度提供候选，不代替身份确认。

Source / 依据与状态

PostgreSQL 保存资料、任务、来源贡献和切片向量归属；文件系统保存原文及准备计划，为追溯、撤回与恢复提供依据。

02

构建有检查点，检索有证据

同一份来源信息贯穿资料导入、知识写入、查询取证与资料删除。

WRITE资料如何进入图谱

  1. 定义业务模型

    声明实体类型、身份字段、关系、原子字段组与结构化映射。

  2. 登记、解析与分块

    保存原文，建立字符或字段位置映射；支持 TXT、Markdown、文本 PDF、CSV 与 JSON。

  3. 抽取与基本校验

    LLM 生成候选，或按显式映射取得字段；校验结构、身份、精确原文及实际输入范围。

  4. 准备完整写入计划

    计算向量、保存对象 ID 与来源贡献；模型和向量调用在正式写入前完成。

  5. 应用、核验与恢复

    写入期间控制知识读取；中断后沿用已保存计划、ID 和向量恢复。

READ问题如何找到依据

  1. 明确问题与资料范围

    支持关键词、自然语言、对象 ID，以及类型、资料和属性过滤。

  2. 多路召回

    精确身份、关键词和向量通道共同提供图对象与原文切片候选。

  3. 合并排名与重排

    采用 RRF 融合，同一对象每通道只计最佳名次；可用 LLM 重排内部候选池。

  4. 读取图与来源

    取得实体详情、邻居或有界路径，并按预算返回实际证据与原文位置。

  5. 返回知识与覆盖信息

    披露冲突、歧义、截断和通道降级；调用方据此决定是否补充检索。

删除资料时：撤回该资料的来源贡献，重新聚合其余来源支持的知识。共享对象不会因单一资料删除而被整体清空，失去全部依据的内容则随维护任务移除。

03

可配置，也明确边界

提供可追溯的知识材料，由调用方完成最终回答、业务计算与执行。

服务负责的事

  • 以业务字段和数据库约束对齐身份，使用随机 UUID 标识对象。
  • 保存精确引用、来源贡献和完整原子字段声明。
  • 支持混合检索、图查询、资料删除、模型重建和向量重建。
  • 对模型错误和证据错误进行有限重试，保留失败原因。
  • 模型完整性标记作为质量信息，不单独否决已有证据支持的正文。

适用边界

  • Top-K 是候选集合，不表示知识库已经完整枚举。
  • 字段和证据校验通过，不等于业务语义已获人工验收。
  • 原文引用必须真实且在输入范围内，不能用近似措辞补造证据。
  • 扫描 PDF、复杂表格、生产并发和高可用仍缺少验收结果。
  • 当前部署采用单 API、单 Worker，应用面向可信环境。

图谱正文覆盖与查询通过数为何不同？

Clause 正文完整覆盖30个官方参考 span 中的20个。该分母还包括日期、主体等非 Clause 标注，因此不能把20/30视为实体正确率；fact、context 与切片覆盖也分别统计。

这轮验证使用了什么配置？

05

从业务模型与运行配置开始

准备 Linux / WSL、Python 3.12、Neo4j 和 Qdrant。安装依赖、配置数据库和模型凭据后，分别启动 API 与 Worker。

# 在仓库目录设置运行配置
export KG_CONFIG="$PWD/configs/app.local.yaml"
export KG_ENV_FILE="$PWD/.env"

# API 与 Worker 均停止时初始化
.venv/bin/kg init-storage

# 在两个终端分别启动
.venv/bin/kg serve
.venv/bin/kg worker

先按运行指南创建虚拟环境、安装依赖并复制配置模板。凭据放在本机 .env 或进程环境变量，API 和 Worker 使用同一份配置。
