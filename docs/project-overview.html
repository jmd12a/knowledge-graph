01

系统架构与读写路径

业务模型定义对象类型、身份和关系。资料维护与在线查询共用业务服务，各自沿独立的写入和读取路径执行。

HTTP 与 MCP 共用检索服务接口 → 服务 → 领域与端口
HTTP

登记资料与任务，也提供知识检索

MCP

为 Agent 提供只读检索工具

写入路径

先准备，再发布

按业务模型解析、抽取、对齐实体，生成带来源贡献的写入计划。准备期间旧知识可查，计划核验后再提交可见状态。

读取路径

查图，也查原文

从图中读取对象和关系，从索引定位原文。查询限定资料时，返回的实体属性和证据也按该范围组织。

图知识

Neo4j 保存当前实体、关系和可查询属性，支持按明确对象与关系条件查询。

检索索引

Qdrant 保存图对象向量和原文切片索引。相同文本可复用向量，来源归属各自保留。

来源与任务状态

PostgreSQL 保存资料、贡献、向量归属与任务状态。原文由文件存储保留。

一条证据的回查路径图对象 → 来源贡献 → 切片与原文位置

关键架构决策

业务身份与来源贡献分开保存
实体按业务身份对齐，每条事实分别记录支持它的资料。撤回一份资料时，只移除它提供的贡献，其他来源仍支持的关系继续保留。
先找候选，再回查证据
关键词和向量帮助定位候选，图查询读取明确的对象与关系。详情分别返回直接支持事实的引用和补充上下文，调用方可以据此判断证据是否足够。
准备与发布分开
抽取和向量计算在准备阶段完成，旧知识仍可查。正式写入按差量计划执行和核验。写入中断时沿用原计划、对象 ID 和向量恢复。
02

一份资料怎样变成可查证据

以合同的最低付款承诺为例，构建要保留共同条件和完整清单，查询要能给出这些内容在原文中的位置。

写入从资料到知识

  1. 登记资料，保留原文

    解析章节、段落或字段，保留标题路径和原文位置。

  2. 按业务规则抽取

    依赖共同条件的付款子项作为一条安排保留，独立义务各自入图。引文逐字核对。

  3. 对齐身份，记录来源贡献

    匹配已有对象须满足配置的身份条件。属性和关系分别保存支持它们的来源。

  4. 核验后发布

    准备好差量和向量后按计划写入，核对图、索引与来源，再将资料设为可查询。

读取从问题到出处

  1. 明确查询范围

    调用方可指定资料、对象类型或属性，也可以用自然语言描述问题。

  2. 查找并排序候选

    融合精确匹配、关键词和向量候选。需要重排时，优先使用已经核验的主要摘录。

  3. 回查条款和支持原文

    读取付款条款详情及同源上下文。需要更多原文时，可以走切片检索。

  4. 返回证据和覆盖信息

    结果给出出处，并披露冲突、歧义、截断或降级，便于决定是否继续取证。

一次查询返回什么

取自当前版的长合同复测。问题用中文简述，原文只展示一小段，覆盖结果对应完整的参考范围。

04

接口与适用边界

提供可追溯的知识材料，由调用方完成最终回答、业务计算与执行。

服务负责的事

  • 以业务字段和数据库约束对齐身份，使用随机 UUID 标识对象。
  • 保存精确引用、来源贡献和完整原子字段声明。
  • 支持混合检索、图查询、资料删除、模型重建和向量重建。
  • 对模型错误和证据错误进行有限重试，保留失败原因。
  • 模型完整性标记作为质量信息，不单独否决已有证据支持的正文。

适用边界

  • Top-K 是候选集合，不表示知识库已经完整枚举。
  • 字段和证据校验通过，不等于业务语义已获人工验收。
  • 原文引用必须真实且在输入范围内，不能用近似措辞补造证据。
  • 扫描 PDF、复杂表格、生产并发和高可用仍缺少验收结果。
  • 默认单 API、单 Worker。可选跨库并行准备与单 Worker 串行发布，应用面向可信环境。

两次运行用的是什么配置？

06

从业务模型与运行配置开始

准备 Linux / WSL、Python 3.12、PostgreSQL、Neo4j 和 Qdrant。安装依赖、配置数据库和模型凭据后，分别启动 API 与 Worker。

# 在仓库目录设置运行配置
export KG_CONFIG="$PWD/configs/app.local.yaml"
export KG_ENV_FILE="$PWD/.env"

# API 与 Worker 均停止时初始化
.venv/bin/kg init-storage

# 在两个终端分别启动
.venv/bin/kg serve
.venv/bin/kg worker

先按运行指南创建虚拟环境、安装依赖并复制配置模板。凭据放在本机 .env 或进程环境变量，API 和 Worker 使用同一份配置。
